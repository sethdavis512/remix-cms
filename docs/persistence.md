# Persistence: PostgreSQL, SQL migrations

**Status:** Accepted (Milestone 1, SQLite); revised 2026-10-09 (PostgreSQL)

## Context

The CMS needs a database that fits the Remix 3 `data-table` layer, which ships
SQLite, Postgres, and MySQL drivers plus a SQL-first migration system. Milestone 1
started on SQLite through Node's built-in `node:sqlite` because it needed no
server and no native build step. The app has since moved to **PostgreSQL** so
local development, tests, and deployment all run against the same engine, and so
JSON content can later be indexed and queried properly (see
[limitations-and-follow-ups](./limitations-and-follow-ups.md)).

## Decision

Use **PostgreSQL** through `remix/data-table/postgres` (backed by `pg`). Schema
changes are **hand-written SQL migrations**; the runtime `table(...)` definitions
mirror them for typed queries.

- Connection: `app/data/db.ts` exposes `openDatabase(url)` around
  `createPostgresDatabase({ connectionString })`. The app uses `DATABASE_URL`
  (default `postgres://localhost:5432/remix_cms`); tests use `TEST_DATABASE_URL`
  (default `.../remix_cms_test`). `pg` connects lazily, so importing the module
  opens nothing. The module also installs a `pg` type parser so `int8` columns
  come back as JavaScript numbers.
- Migrations: plain SQL in `db/migrations/<timestamp>_<slug>/up.sql` (and
  `down.sql`). The `remix db` CLI applies them using the adapter and directory
  declared in `remix.json` (`npm run db:reset` for first-time setup,
  `db:migrate`, `db:rollback`, `db:status`); tests call `db.reset({ migrations })`
  directly. `db/seed.ts` creates the first admin (`npm run db:seed`).
- Types: ids are `integer generated by default as identity`; timestamps are
  epoch milliseconds in `bigint` columns (a 32-bit `integer` overflows). In
  `app/data/schema.ts` those columns stay `c.integer()` so rows type as `number`,
  which the int8 parser guarantees at runtime. JSON blobs (`entries.data`,
  `content_types.schema`, `components.schema`) stay `text` and are parsed in the
  `*.server.ts` modules; the public API's field filters cast with
  `data::jsonb ->> 'field'`.
- Raw SQL: the `rawSql('... ?', [...])` escape hatch keeps `?` placeholders; the
  Postgres compiler rewrites them to `$n`.

## Why

- **One engine everywhere.** The same migrations and queries run locally, in
  tests, and in production, so dialect differences cannot hide until deploy.
- **Migrations own DDL, schema.ts documents it.** Per the framework guidance,
  migrations are the immutable source of truth for the actual database shape;
  `app/data/schema.ts` mirrors columns for typed reads/writes but does not create
  tables. Migrations never import app code, so replaying them stays stable.
- **Room to grow.** `jsonb` operators and indexes are available when JSON
  filtering needs to be faster than a per-type scan.

## Consequences

- **A Postgres server is a prerequisite** for `npm run dev` and `npm test`.
  Node >= 24.3 is still required by the `remix` package itself.
- **Tests share one database.** `app/router.test.ts` drops and recreates
  `remix_cms_test` once per run and truncates the app tables before each test.
  This is safe because tests in a file run sequentially; a second DB-backed test
  file would need its own database name. See [testing](./testing.md).
- The migration SQL was rewritten in place for Postgres when switching. Existing
  SQLite files are not migrated; regenerate sample data with `npm run db:generate`.
- Timestamps are stored as epoch-millisecond integers.
- The generic content model (see [data-model](./data-model.md)) means only a
  handful of real tables exist regardless of how many content types are created
  (plus the `data_table_migrations` journal).

## Where it lives

- `app/data/db.ts`, `app/data/schema.ts`
- `db/migrations/*/{up,down}.sql`, `remix.json`, `db/seed.ts`
